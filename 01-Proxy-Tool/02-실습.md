
# Burp Suite 기초 실습
## 1. 실습 개요
### 1.1 실습 목적
Burp Suite 를 활용하여 클라이언트와 웹 서버 사이에서 발생하는 HTTP 요청 및 응답을 확인하고, Proxy Tool의 기본적인 작동 원리를 이해한다.

### 1.2 실습 환경

운영체제: Windows

실습 도구: Burp Suite Community Edition

버전: v2026.10.1

실습 사이트:
- https://example.com
- https://portswigger.net
- https://postman-echo.com

사용 기능: Proxy, HTTP history, Intercept, Repeater, Burp 내장 브라우저

## 2.  Burp Suite 실행 및 설정
Burp Suite Community Edition을 설치한 후 실행하였다.

프로젝트 생성 단계에서 `Temporary project in memory`를 선택하고, 설정 단계에서는 `Use Burp defaults`를 선택하였다.

이후 `Start Burp`를 클릭하여 프로그램을 실행하였다.

### 2.1 Proxy 기능 확인

상단 메뉴에서 `Proxy → Intercept`로 이동하였다.

초기 화면에는 `Intercept is off`라고 표시되어 있었다.

이는 HTTP 요청을 중간에서 일시 정지하는 기능이 비활성화된 상태를 의미한다.

이 상태에서도 HTTP 통신 내용은 `HTTP history`를 통해 확인할 수 있다.

### 3.3 HTTP Request 분석

HTTP history에서 확인한 요청을 선택하여 'Request' 탭의 내용을 분석하였다.

실제 요청의 주요 내용은 다음과 같다.

```http
GET / HTTP/1.1
Host: example.com
Sec-Ch-Ua-Platform: "Windows"
Accept-Language: ko-KR, ko;q=0.9
Accept-Encoding: gzip, deflate, br
Connection: keep-alive
```

실제 HTTP 요청 중 주요 항목만 발췌

**① GET / HTTP/1.1**

HTTP 요청의 시작 부분으로, 요청 메서드와 경로 및 프로토콜 버전을 나타낸다.

- GET: 서버에 리소스를 요청하는 메서드
- /: 웹사이트의 최상위 경로
- HTTP/1.1: Burp Suite에 표시된 요청의 HTTP 버전

**② Host: example.com**

요청 대상 호스트를 나타낸다.

**③ Sec-Ch-Ua-Platform: "Windows"**

클라이언트의 운영체제와 관련된 정보를 전달한다.

**④ Accept-Language: ko-KR,ko;q=0.9**

클라이언트가 선호하는 언어를 나타낸다. 이번 요청에서는 한국어가 우선적으로 설정되어 있었다.

**⑤ Accept-Encoding: gzip, deflate, br**

클라이언트가 처리할 수 있는 콘텐츠 압축 방식을 나타낸다.

이번 분석을 통해 브라우저가 웹사이트에 접속할 때 요청 경로뿐만 아니라 브라우저 환경 및 데이터 처리와 관련된 정보도 함께 전달한다는 사실을 확인하였다.

## 4. HTTP Response 분석

### 4.1 HTTP 응답 확인

HTTP Request 분석에 이어 같은 통신 기록의 `Response` 탭을 선택하였다.

서버가 반환한 응답에는 HTTP 상태 코드, 응답 헤더, HTML 본문 등이 포함되어 있었다.

<img width="1432" height="1698" alt="image" src="https://github.com/user-attachments/assets/b67b9a01-98b3-42d7-bbbf-c62ed921bdf2" />

### 4.2 HTTP 응답 헤더 분석

실제 응답에서 확인한 주요 내용은 다음과 같다

```http
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
Server: cloudflare
Cf-Cache-Status: HIT
```

**1) HTTP/2 200 OK**

`HTTP/2` 는 응답에 표시된 HTTP 프로토콜 버전이며, `200 OK` 는 서버가 요청을 정상적으로 처리했음을 의미. 단, 요청이 정상적으로 처리되었다는 사실이 해당 웹사이트의 보안이 안전하다는 의미는 아님

**2) Content-Type: text/html; charset=utf-8**

서버가 반환한 데이터의 형식과 문자 인코딩을 나타낸다.

`text/html`은 HTML 문서임을 의미, `charset=utf-8` 은 UTF-8 문자 인코딩을 사용한다는 뜻

**3) Server: cloudflare**

응답을 처리한 서버와 관련된 정보를 나타내는 헤더

이번 응답에서는 Cloudflare가 표시됨.

**4) Cf-Cache-Status: HIT**

Cloudflare의 캐시에 저장된 응답이 제공되었다는 의미

캐시는 이전에 가져온 데이터를 저장해 두었다가 재사용하는 기능으로, 서버의 부담을 줄이고 응답 속도를 개선하는 데 사용됨.

### 4.3 HTML 본문 분석

HTTP 응답은 헤더와 본문으로 구분됨

헤더: 응답 상태, 데이터 형식 등의 정보 포함

본문: 실제로 전달하는 데이터 포함

이번 응답에서는 HTML 코드가 반환되었으며, 다음을 확인하였다.

```html
<title>Example Domain</title>
```

`<title>` 태그는 웹페이지의 제목을 지정하는 HTML 요소이다.

실제 브라우저에서도 `Example Domain` 이라는 제목이 표시되었으므로 서버가 반환한 HTML 데이터가 브라우저에서 해석되어 웹페이지로 나타난다는 것을 확인할 수 있었다.

이를 통해 HTTP Request 는 클라이언트가 서버에 보내는 요청이고, HTTP Response는 서버가 요청을 처리한 후 반환하는 결과라는 차이를 이해하였다.


## 5. Intercept 를 이용한 HTTP 요청 가로채기

### 5.1 Intercept 기능 활성화 및 요청 확인

앞선 실습에서는 `HTTP history`를 통해 HTTP 요청과 응답을 확인하였다.

이번에는 `Intercept` 기능을 사용하여 HTTP 요청이 서버로 전달되기 전에 일시 정지되는 과정을 확인하였다.

**실습 과정**

1. Burp Suite의 `Proxy -> Intercept` 메뉴로 이동하였다.
2. `Intercept off` 버튼을 클릭하여  `Intercept on` 으로 변경하였다.
3. Burp 내장 브라우저에서 `https://portswigger.net` 에 접속하였다.
4. Burp Suite 에서 해당 요청이 중간에 멈춘 것을 확인하였다.

**확인한 결과**

- Intercept 상태: on
- Method: GET
- 요청 URL: https://portswigger.net/
- Host: portswigger.net
- 요청 경로: /

HTTP 요청이 가로채진 상태에서는 브라우저가 서버의 응답을 기다리게 된다.

이는 Burp Suite 가 요청을 중간에서 일시 정지시켰기 때문이다.

또한 화면에 `Forward` 와 `Drop` 버튼이 활성화되어 있는 것을 확인하였다.

- **Forward** 가로챈 요청을 다음 단계로 전달하는 기능
- **Drop** 요청을 폐기하여 서버로 전달되지 않도록 하는 기능

  이 기능을 활용하면 요청이 서버에 전달되기 전에 그 내용을 확인하고, 필요한 경우 수정할 수 있다.

  <img width="1438" height="1710" alt="image" src="https://github.com/user-attachments/assets/b8819419-883d-4a6b-8a5d-db9f08de9029" />


### 5.2 Forward 기능을 통한 요청 전달

Intercept 기능으로 GET 요청을 가로챈 상태에서 `Forward` 버튼을 클릭하였다.

이후 이미지, 글꼴, 스크립트 등을 요청하는 추가 HTTP 요청들이 나타나는 것을 확인하였다.

이는 하나의 웹페이지를 표시하기 위해 여러 리소스에 대한 요청이 발생할 수 있기 때문이다.

추가 요청을 전달한 후 Burp 내장 브라우저에서 PortSwigger 웹페이지가 정상적으로 표시되는 것을 확인하였다.

이번 실습을 통해 Forward는 일시 정지된 개별 요청을 전달하는 기능이며, Intercept off는 이후 요청을 자동으로 전달하도록 하는 설정이라는 차이를 이해하였다.

## 6. Repeater 를 이용한 HTTP 요청 재전송

### 6.1 Repeater 기능 및 실습 목적

Repeater는 HTTP 요청을 직접 전송하고, 서버가 반환하는 응답을 확인할 수 있는 Burp Suite의 기능이다.

기존 요청을 수정하거나 반복적으로 전송할 수 있어 서버가 특정 요청을 어떻게 처리하는지 분석하는 데 활용된다.

이번 실습에서는 HTTP history에서 확인한 요청을 Repeater로 전달하고, 동일한 요청을 다시 전송하여 서버의 응답을 확인하였다.

### 6.2 HTTP 요청 재전송

**실습 과정**

1. `Proxy → HTTP history`에서 PortSwigger의 메인 페이지에 대한 GET 요청을 선택하였다.

2. 해당 요청을 마우스 오른쪽 버튼으로 클릭한 후 `Send to Repeater`를 선택하였다.

3. `Repeater` 탭에서 요청이 정상적으로 불러와진 것을 확인하였다.

4. 요청 내용을 변경하지 않은 상태에서 `Send` 버튼을 클릭하였다.

5. 서버가 반환한 HTTP 응답을 확인하였다.

**확인한 요청**

GET / HTTP/2
Host: portswigger.net

**확인한 응답**

HTTP/2 200 OK
Content-Type: text/html

- 응답 상태 코드: 200 OK
- 응답 데이터 크기: 85,858 bytes
- 표시된 소요 시간: 316 ms

`200 OK`를 통해 요청이 정상적으로 처리되었음을 확인하였고, `Content-Type: text/html`을 통해 HTML 형식의 데이터가 반환되었음을 알 수 있었다.

### 6.3 실습을 통해 이해한 내용

앞선 Intercept 실습에서는 브라우저가 보낸 요청을 중간에서 일시 정지한 후 Forward로 전달하였다.

반면 Repeater에서는 기존 HTTP 요청을 별도로 가져와 Send 버튼으로 직접 재전송할 수 있었다.

이를 통해 Repeater가 브라우저에서 동일한 작업을 반복하지 않고도 HTTP 요청을 테스트하고 서버의 응답을 분석할 수 있도록 돕는 기능임을 이해하였다.


### 6.4 HTTP 요청값 수정 및 응답 비교

Repeater의 요청 수정 기능을 이해하기 위해 HTTP 테스트 서비스인 Postman Echo를 활용하였다.

이번 실습에서는 GET 요청의 쿼리 매개변수를 변경하고, 변경 전후의 서버 응답을 비교하였다.

**1) 수정 전 요청 전송**

Burp 내장 브라우저에서 다음 주소에 접속하였다.

`https://postman-echo.com/get?item=apple`

HTTP history에서 해당 요청을 선택하고 `Send to Repeater` 를 통해 Repeater 로 전달하였다.

이후 `Send` 버튼을 클릭하여 서버 응답을 확인하였다.

요청의 주요 내용은 다음과 같다.

`GET /get?item=apple HTTP/2`

응답의 JSON 데이터에서 다음 값을 확인하였다.

`"item": "apple"`

이를 통해 서버가 요청에 포함된 쿼리 매개변수 `item` 의 값인 `apple` 을 전달받았음을 확인하였다.

<img width="575" height="682" alt="분석 출력 1" src="https://github.com/user-attachments/assets/e3bce57c-4ce7-4dc3-9f7b-83a206e6de02" />


**2) 요청값 수정 및 재전송**

Repeater의 Request 영역에서 `apple`을 `banana` 로 수정하였다.

수정한 요청은 다음과 같다.

`GET /get?item=banana HTTP/2`

이후 `Send` 버튼을 다시 클릭하였다.

응답의 JSON 데이터에서 다음 값을 확인하였다.

`"item": "banana"`

이를 통해 HTTP 요청에 포함된 값을 변경하면 서버가 전달받는 값도 변경된다는 사실을 확인하였다.

### 6.5 실습 결과 및 분석

이번 실습에서는 Repeater를 사용하여 HTTP 요청에 포함된 쿼리 매개변수를 직접 수정하고, 서버의 응답을 비교하였다.

수정 전에는 `apple`이 반환되었고, 수정 후에는 `banana`가 반환되었다.

Postman Echo는 요청받은 매개변수를 응답에 다시 표시하는 서비스이므로, 이러한 결과를 통해 수정한 값이 서버에 정상적으로 전달되었음을 확인할 수 있었다.

또한 Repeater를 활용하면 브라우저에서 동일한 작업을 반복하지 않고도 요청값을 변경하고 서버의 반응을 비교할 수 있다는 점을 이해하였다.

다만 이번 실습에서 응답값이 변경되었다는 사실만으로 보안 취약점이 존재한다고 판단할 수는 없다.

실제 웹 보안 진단에서는 이러한 기능을 활용하여 서버의 입력값 검증이나 접근 권한 검사 등이 적절하게 이루어지는지 분석할 수 있다.
